# Agent 辅助切片方案（提案，未实施）

> 背景：V0.5 的切片对「层次分明」的 Markdown（标题树）效果很好，但对**无结构 / 半结构化文本**——聊天记录、零散笔记、大段连续论述、Transcript——效果差：fixed 滑窗只保证长度，不保证语义完整，切出来的块可能一句话说一半、或者一个主题混两块。

## 目标

让没有清晰标题结构的文档也能切出**语义完整、主题单一**的 chunk，保持 V0.5 的硬约束不变（原文不可变、溯源必填、双粒度）。

## 方案对比

### 方案 A：LLM 语义边界标注（推荐）

**思路**：不用 LLM 直接切片，而是让它做「断句处打分」。流程：

1. 先用现有 fixed/滑窗把文档切成**候选段**（粗粒度，比如 1500 token 一段，句子边界对齐）；
2. 对每个候选段，LLM 只回答一个结构化问题：「这一段内部有哪些主题转折点？给出每个转折点所在句子的编号和 5–10 字的主题标签」；
3. 程序按转折点把候选段切成语义 chunk，主题标签写入 `title_path`（无标题文档就有溯源标题了）；
4. 产出仍走现有 `Chunker` 接口——新增一个 `agent` 实现，接口不用改。

**优点**：
- 输出是「转折点坐标」而非切好的文本，LLM 不碰原文，天然满足**原文不可变**（我们只是读取坐标）；
- token 消耗约为文档的 1 倍多一点（只需读入，输出极短）；
- 失败可降级：LLM 超时/解析失败 → 回退现有 fixed 切片，导入永不阻塞。

**缺点**：转折点粒度控制要调 prompt；超长文档要分段调用。

### 方案 B：LLM 生成虚拟标题树

**思路**：让 LLM 通读全文，输出一份「虚拟目录」（JSON：主题 → 小节 → 涉及的行号区间），程序按目录切分，目录直接当 `title_path`。

**优点**：结构最好，溯源标题天然语义化。
**缺点**：行号区间是 LLM 输出，**容易幻觉错位**（数错行），需要校验+重试逻辑；长文档上下文压力大。适合作为 A 的后续增强（A 切完块后，再对块集合生成目录）。

### 方案 C：纯本地信号 + 少量 LLM（省 token）

**思路**：先用本地信号找候选边界（语义相似度突降——相邻句子 embedding 余弦距离跳变、指代词"这/那/它"开头的句子、话题词频突变），只把「模糊地带」发给 LLM 确认切不切。

**优点**：token 消耗最小（约文档的 10–20%）。
**缺点**：实现复杂度高，召回不全时切错。适合以后优化，不适合第一版。

## 推荐：先 A 后 B 增强

```
导入 .txt / 无标题 .md
        │
        ▼
  粗切（1500 token 候选段，句子边界）
        │
        ▼
  LLM 标注转折点（JSON：[{sentence_idx, topic}]，失败→回退 fixed）
        │
        ▼
  按转折点细分 → title_path = "虚拟主题标签"
        │
        ▼
  现有流程照常：>1000 二次切 / <100 合并 / 双粒度 / 向量化
```

## 关键设计点（实施时再细化）

1. **接口落位**：`chunker.AgentChunker` 实现 `Chunker` 接口；导入时按文档特征选择——有 ≥3 个 H2 标题走 `heading`，否则走 `agent`（设置页加开关「智能切片」）；
2. **prompt 约定**：要求 LLM 输出严格 JSON（`{"breakpoints": [{"line": n, "topic": "..."}]}`），程序校验 line 必须落在候选段行号范围内，非法坐标丢弃；
3. **溯源不变**：chunk 仍引用原文行区间，`title_path` 是 LLM 起的标签（属于 metadata，不属于原文，不违反不可变约束）；
4. **成本预估**：1 万字文档 ≈ 1.5 万 token 输入 + 几百输出，DeepSeek 约 ¥0.02，可忽略；
5. **评测**：准备 3–5 篇典型无结构文档（聊天记录/读书笔记），人工标注理想切点，对比 A/C 的切点命中率，达标（>80%）再上线。

## 工作量预估

方案 A：后端 1–1.5 天（AgentChunker + prompt + 降级 + 单测）、前端半天（开关 + 生成中提示）；方案 B 增强再加 1 天。
